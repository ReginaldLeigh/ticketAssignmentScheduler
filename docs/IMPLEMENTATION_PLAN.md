# Ticket Assignment Scheduler — Implementation Plan

**Status:** v12, **APPROVED AND BUILT** (updated 2026-11-17). v12 adds change request 2026-11-16 (`claude/change-request-2026-11-16.md`): teams and roles, range scheduling, developer-only settings, the Ivanti ID lookup, team and shared queues, and the dark-mode modal fix.
**Code:** v12 is on GitHub at `ReginaldLeigh/ticketAssignmentScheduler` (`main`), in the original multi-file layout (`src/`, `tests/`, `tools/`, `docs/`). Build outputs (`dist/`, `preview/`) are not committed; regenerate them with `npm run condense` and `npm run demo`. A 3-file quick-test build (`Code.gs`, `Index.html`, `appsscript.json`) is generated by `tools/condense.py`. A click-through demo is built by `tools/build_demo.py` into `preview/demo.html` and published as the "Mailbox rota demo" artifact.
**Platform:** Google Apps Script (HtmlService web app, time-driven triggers, BigQuery Advanced Service), Ivanti Neurons for ITSM, BigQuery, Google Sheet.

> **No table creation.** The app never creates, alters or drops a BigQuery dataset, table, view or temporary table, or a Google Sheet tab or column. A developer creates everything listed in §9 by hand. The app reads and writes **rows** only. If anything is missing, runs stop and the Setup check lists exactly what to create. Code that would create a table is blocked at runtime and **fails unit testing**.

## 1. Requirements

**Backend**
- Pick up new Incidents from Ivanti and set the Owner once assigned.
- Route each ticket by each team's rules (all conditions in a rule must match; a mailbox can have several rules), teams in `TEAMS` order, mailboxes in priority order. The first match wins.
- Follow-ups go to the earlier owner within the team. New tickets go to a random scheduled, Ivanti-linked employee, within ±1.
- Unmatched tickets go to Vertex AI (added later), choosing among rule-less mailboxes, then to the shared queue.
- Look up each person's Ivanti ID from their email with the developer's function.
- All queries and developer settings live in one developer-editable file. Changes from several users at once are safe. No table creation.

**Frontend**
- Managers and admins manage their team's employees, mailboxes, rules, team settings and schedule, including scheduling someone for a week or more at once. Managers manage admins.
- Every role can view their team's weekly schedule and mailboxes, and use Run now. Pages refresh on their own.
- Modals stay readable when the browser is in dark mode.

## 2. Access model (D25, D28)

| Who | Needs |
|---|---|
| Employees | A Google account in your Workspace domain, and their email on their team's **Roster** |
| Admins | The same, plus their email on the team's **Admins** list (added by a manager in the app) |
| Managers | Their email in `TEAMS` in `QueryConfig.gs` (developer-set) |
| **The app's account** | BigQuery Job User on the project; **Data Editor on each approved table, granted per table, never on the dataset**; edit access to the Sheet; the Ivanti API key (a Script Property, never shown to users) |

- Anyone not on a team is refused: *"You're not on a team in this app yet. Ask your manager to add you."*
- Role is decided as manager > admin > employee. Every API call is checked against the caller's role and team on the server.
- **Use a dedicated shared account** (e.g. `ticket-scheduler@yourco.com`), not a person's own account.
- Granting Data Editor per table, rather than on the dataset, means **BigQuery itself refuses table creation**, a second safeguard for D23.

## 3. Architecture

```
          Ivanti ITSM (Incidents) ◄──────── set Owner ──────────────┐
                 │ REST API key          ▲ employee lookup (email)   │
 ┌───────────────▼───────────────────────┼─ Apps Script project ─────┼──┐
 │ Per-team run: Ivanti → Rules (teams in order) → FollowUp           │  │
 │        → Balancer (±1, linked people) → MERGE rows → Writeback ────┘  │
 │        no rule → cross-team follow-up → Vertex (rule-less mailboxes)  │
 │        → team queue / shared queue (vertex_queue rows)                │
 │ Browsers ─► WebApp (role + team check) ─► Store (team-scoped) ─► Sheet│

```

The source is split into one `.gs` file per component in `src/`. `tools/condense.py` merges them into a single `Code.gs` plus one `Index.html` for quick testing.

## 5. Assignment run (one team at a time)

1. **Run lease.** Only one run at a time across the app. Others see which team's run is going and who started it.
2. **Checks.** Run `checkConfig()` (including `TEAMS` and `DEVELOPER_SETTINGS`) and `checkSchema()`. If anything is missing, **stop and report it**; never create it.
3. **Link people.** Look up Ivanti IDs for the team's active, unlinked people (outside the save lock).
4. **Snapshot** all teams' config under a short lock. Edits saved mid-run apply to the next run.
5. **Retry** the team's failed or pending Ivanti updates.
6. **Fetch** Incidents from Ivanti, oldest first. **Skip** tickets already assigned or being changed by hand.
7. For each ticket, routing is the same whichever team is running:
   1. **Rules**, teams in `TEAMS` order, mailboxes by priority (only mailboxes with rules). The match gives the team and mailbox.
   2. **Follow-up within that team:** goes to the earlier owner, not counted toward the split.
   3. Otherwise **balance** among the team's scheduled, Ivanti-linked people (lowest count wins, ties at random). Nobody scheduled → team queue (`no_one_scheduled`); only unlinked people scheduled → team queue (`no_linked_employee`).
   4. **No rule matched:** follow-up check across all teams. A match joins the earlier ticket's team.
   5. **Vertex** (stub today), choosing among rule-less mailboxes on any team.
   6. Still nothing → **shared queue**.
   - Tickets that land on another team are left in Ivanti for that team's run.
8. **Save rows** (`MERGE`, status `pending`), then **set the Owner** in batches of 25, then record the result.
9. **Record the run row and release the lease.** Close to the 6-minute limit, it continues in a follow-up run.

**Schedule:** one 10-minute ticker checks every team's run times and days (default 06:00 and 13:00, Mon–Fri, America/New_York) and runs each team's slot once. **Run now** runs the clicking person's team, with a per-team cooldown. **Dry run** is for managers and admins.

## 6. Subject matching (D9)

- **Clean-up:** lowercase; strip leading `RE:`/`FW:`/`[EXT]` (repeated); non-alphanumerics become spaces; drop the team's stop words. Numbers are kept.
- **Score:** the higher of word overlap and containment.
- **Match:** score ≥ `SUBJECT_MATCH_THRESHOLD` (developer setting, 0.75). The best score wins; a tie goes to the most recent.
- **Never follow-ups:** fewer than `SUBJECT_MIN_WORDS` (3) meaningful words, or on the team's ignore list.
- The same rules run in JavaScript and in BigQuery SQL. A test cross-checks the two.
- **Team settings → Test a subject** shows the top matches in the team's history.

## 7. Simultaneous use (D22)

- **Short lock** around every save; **permanent IDs and soft deletes**; **version checks** with **Re-apply my change** or **Discard mine**; **request IDs**; **all-or-nothing saves**; checks against current data inside the lock.
- **Team scoping in the Store:** reads see only the caller's team; writes are stamped with it; a reference to another team's record is refused.
- **One team per person** is checked inside the save lock.
- **Ivanti lookups run before the lock**, so a slow lookup never blocks other people.
- **Range scheduling** saves every day or none, skipping days already scheduled.
- **Shared-queue claims:** a version-checked `MERGE`; the second team sees *"<Team> already took this ticket."*
- **Run lease** separate from the save lock. **Auto-refresh** per team every 30 s. **Audit log** per team, with Ivanti IDs shown as `[hidden]`.

## 9. Tables (D23): created by a developer

Full SQL, column descriptions, permissions and Sheet headers are in **`docs/SCHEMA.md`**. A **`REQUIRED TABLE`** note with the full schema sits above each table's setting in `QueryConfig.gs`.

### 9.1 BigQuery (Option A, approved; `team_id` columns approved 2026-11-16)

| ID | Table | Why it's needed |
|---|---|---|
| **P1** | `assignments` | One row per assigned ticket: history for follow-ups, ±1 counts, duplicate check, Ivanti retries, Assignment Log. **`team_id STRING NOT NULL`.** Partitioned by `DATE(assigned_at)`, clustered by `team_id, mailbox_id, employee_id`. |
| **P2** | `runs` | One row per team run. **`team_id STRING NOT NULL`.** Partitioned by `DATE(started_at)`, clustered by `team_id`. |
| **P3** | `vertex_queue` | One row per unrouted ticket, with the Vertex payload. **`team_id STRING` (NULL = shared queue)** and **`claimed_by_team STRING`**. Status adds `no_linked_employee`. Clustered by `team_id, status`. |

**No new tables.**

### 9.2 Google Sheet tabs (developer-created)

`Mailboxes`, `Rules`, `Employees`, `Schedule`, `Admins`, `Settings`, `SubjectIgnoreList`, `StopWords`, `AuditLog`. Every tab gains `team_id`. **Employees** gains `ivanti_lookup_status` and `ivanti_checked_at`. **Settings** becomes `id, team_id, key, value, …` and holds only `RUN_TIMES` and `RUN_DAYS`. Exact headers are in `docs/SCHEMA.md`.

### 9.3 Enforcement

- **Runtime:** the BigQuery component is the only BigQuery caller: single `SELECT`/`INSERT`/`MERGE` statements only, DDL and scripting rejected, allow-listed request fields, and only `Jobs.query`, `Jobs.getQueryResults` and `Tables.get`. The Store is the only Sheet caller and only reads and writes ranges on existing tabs. Per-table IAM grants mean BigQuery itself refuses creation.
- **Unit tests** (`tests/noTableCreation.test.js`, run against the source and the single-file build): source scan with a self-test; every real SQL statement passes the guard and 27 forbidden ones are rejected; a "full day of use" makes zero creation calls; missing tables or columns stop the run and create nothing.

## 12. Build notes (where the build refines the plan)

- **Column names:** the runs column `trigger` was renamed **`trigger_type`**.
- **Where unrouted tickets live:** P1 holds **assigned tickets only**. Unrouted tickets live in P3.
- **Tab headers:** `Admins`, `SubjectIgnoreList` and `StopWords` have an **`active`** column (soft delete).
- **Stop words:** the built-in list is used until a team adds one. Adding any word replaces the built-in list for that team.
- **Managers aren't on the Admins tab;** they come from `TEAMS`. A manager on two teams fails the setup check.
- **Shared-queue processing:** `processVertexQueue()` re-tries pending shared-queue rows once Vertex exists, and gives each confident answer to the team that owns the chosen mailbox.
- **Demo:** `preview/demo.html` bundles the test mocks, so it lives outside `dist/` and is never deployed. It shows two teams (Billing Support, Payments) and switches between a manager, an admin, an employee and the other team's manager.
- **Tests:** **95 tests** (`npm test`; `npm run test:dist` for the single-file build), including 26 in `tests/teams.test.js` for isolation, roles, the one-team rule, the lookup, no-ID-leak, audit redaction, range scheduling, routing order, cross-team follow-ups, Vertex candidates, team and shared queues, and the claim race. No dependencies; Apps Script services are mocked.
- **Not yet run against real services:** the Ivanti OData details, the lookup function's real response shape (`idPath`), and the BigQuery SQL are written to the documented APIs. The shadow week is where that's confirmed.
